## 2. 最も重要な設計上の分離

### 操作を成功させるエージェントと、利用者を再現するエージェント

既存の`requestFor`はGoal達成のための次の操作を求めている。これは操作エージェントとして自然だが、仮想ユーザーの評価目的とは異なる。

提案する二つのモード：

- `task-solver`：目的達成を優先する。現在の探索機能を維持する。
- `user-simulator`：そのユーザーが、その時点で認識・理解・記憶している情報に基づき、どう行動するかを予測する。

同じ場所に戻ること、途中でやめること、正解を選べないことは、後者では必ずしもエージェントの故障ではない。一方、APIエラーやクリック失敗を人間の迷い・離脱とみなしてはいけない。

安全境界は両モードで維持する。金銭移動・実注文・実メール送信等を許すことで「人間らしさ」を実現しようとしない。

### モデルの確率と、人間の行動確率

TypeSafeのChoiceは選択肢の分布と最大確率のchoiceを返す。[S11](research.md#s11-typesafejev公式仕様)

この分布を保存するだけでは、確率的な行動実行にはならない。また、分布からサンプリングしても、それだけで実ユーザーの選択頻度に一致するとは限らない。

分けて保存する：

1. モデルが返した分布。
2. 校正や安全フィルタを経た実際の選択分布。
3. その分布から選ばれた行動。
4. 人間の観測分布。

## 3. 目標とする構成（提案）

```text
ユーザー仕様書 ＋ 利用目的・チャーター ＋ 対象集団の構成
                         ↓
                  個体と初期状態の生成
                         ↓
実際の画面・時間変化 → 視覚制約・注意選択 → 知覚した情報
                         ↓
             理解・誤解・期待・記憶・感性状態の更新
                         ↓
                行動分布 → 行動の選択 → ブラウザー操作
                         ↑                         ↓
                         └──────── 観察の繰り返し ─┘

別系統：実際の処理結果・基盤障害・安全制約を監査
                         ↓
                個体別／集団別の結果と不確実性
                         ↓
          変更前後の比較 → 設計改善 → 新しい試行で再評価
```

注視先の選択とUI操作は別アクションにする。観察履歴とユーザーが利用可能な記憶も分ける。監査用DOM・正解手順・成功フラグは、ユーザーの知覚に混ぜない。

最終的に必要な性能は、操作の上手さだけではなく、**誰がどこで気づかず、どう解釈し、どこでやめ、変更によってその分布がどう変わるかを予測できること**。視線再現はその手段であり、視線指標が良くなるだけでβテスト全体の妥当性が証明されたとはしない。

## 4. 直近の作業の順序

1. **T00：最新実装の所在を確定。** 作業版とこのスナップショットを対応付ける。
2. **T01・T02：部品の境界と比較基盤。** 観察・状態・行動・監査を分離し、どの変更が何に効いたか測れるようにする。
3. **R01〜R04：モデル・データ・確率・感性の追加調査。** T03〜T06の実装判断に使う。
4. **T03〜T06：視覚、注意、ユーザー状態、行動分布。** 全てを一度に変更せず、機能単位で比較する。
5. **T07・T08：人間との一致と母集団。** 調整用と未見評価用を分ける。
6. **T09・T10：大規模実行と改善ループ。** 工学的な拡張性と、人間への予測妥当性を別々に確認する。

T07の評価設計・データ探索は早期に並行して始める。モデル完成まで比較データの検討を後回しにしない。これは販売開始の段取りではなく、完成形へ向けて不足を埋める順序である。
