# 画像から具体的な条件を抽出する比較

この変更は、現在の候補に対する根拠を現在画像へ限定する修正と、具体的な条件を画像から取り出す段階を分けて比較する。
既定の Jev 方式は維持する。
三度の入力上限停止から画像参照名の衝突を特定した。修正版では既知の失敗画面を通過し、Responses の実応答も取得したが、最初の抽出は根拠条件に違反して停止した。

## 入力と判断

`experience-action-relations` は前フェーズの役割判定である。
`experience-action-relations-current` は `actionRelations.evidencePolicy: "current-candidate"` を追加し、現在候補の根拠を現在画像に限定する。
過去の条件根拠は既存の全体状況の `availabilityEvidence` に保持し、候補別の文脈質問・記録は追加しない。
現在の根拠がない候補は `unknown` とし、過去画像に同じ番号があることを代用にしない。

`experience-visual-conditions` は後者を継承し、`visualHypotheses: {enabled: true, capacity: 3}` を追加する。
OpenAI Responses の `gpt-6-luna` が、実際に添付する現在画像と限定された過去画像から、最大 3 件の条件、転記した短い根拠、候補との関係、操作後に確認する結果を JSON で生成する。
その後、既存の Jev による評価、行動の 2 段階へ渡す。
この抽出段は行動を選ばず、操作確率も生成しない。

引用には `model-transcribed-unverified` を付ける。
画像ハッシュの一致と、転記や条件解釈の正しさは別である。
記憶するのは最大 3 観察分の仮説（各観察の条件は最大 3 件）であり、以前の仮説を現在の画面の事実として扱わない。
DOM、候補ラベル、座標、監査ログ、正解判定、人間の操作や感想は抽出段へ渡さない。
固定のペルソナが指定された場合は保持するが、今回の比較にはペルソナを指定しない。

接続は [Responses の構造化出力](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)と[画像入力](https://developers.openai.com/api/docs/guides/images-vision)の公式仕様に従う。
`store: false`、ツールと会話状態なし、最大 4,000 出力トークン、要求ごとに 30 秒以内、再試行なしとする。
HTTP 成功後の拒否、未完了、不正 JSON、形式不正は、通信失敗と別に保存して停止する。
形式が正しいことから、画像の理解や人間への一致を結論しない。

## 比較条件

図書予約と講習予約の 2 課題に、それぞれ別入口への切替、確認で前提が変わる条件、別途照合が必要な条件を設ける。
各条件で三方式を 1 回ずつ実行し、予定は 18 試行である。
方式の実行順を条件ごとに回し、同じ製品画像、目的、初期状態、許可した情報を照合する。
現在根拠の修正と、具体条件の追加を別々の差分として保存する。

全体の上限は 504 要求、40 分、並列数 1 とする。
各試行は 12 判断、15 UI 操作、3 注視、180 秒以内とし、旧方式と現在根拠方式は 24 要求、抽出あり方式は 36 要求以内とする。
各 API 段階の上限は 12 要求である。
HTTP 400、認証、利用制限、会計不明、抽出形式不正では次の試行へ進まない。
再試行、失敗枠の置換、保存済み入力の直接再送は行わない。

`manifest.json` に予定枠、版、設定、要求台帳、初期画像の照合、原本保全を記録する。
`summary.json` は方式ごとの分母、成功、上限終了、基盤障害、実際の前提変更、照合、再訪、保存を分ける。
各試行には実際の画像、条件仮説、両段階の Jev 入力、元の分布と補正後分布、選択、実操作、終了理由、trace、リプレイ結果を残す。
API 待ち時間は人間の行動時間とは別に扱い、未報告の費用は 0 とせず不明のまま残す。

## 検証の範囲

部品テスト、実ブラウザーを使う通信スタブ、モック比較と実モデルの成績は分ける。
独立検証では、失敗証拠の削除や成功応答の偽造をリプレイが受理する問題、余計な抽出記録の受理、HTTP 200 受領済み失敗の誤集計、宣言外の質問変更の見逃しを再現した。
修正前の証拠を保持し、修正後の版を別のハッシュで再検証する。

この比較は各条件 1 試行なので、再現性や一般的な改善率は検証できない。
人間との一致、転記と条件解釈の正確さ、他画面への一般化は別の検証が必要である。

## 初回の実モデル停止

初回 producer は `abe56582c179a3cce6c9e6e59a70f814e368e527` である。
予定 18 試行のうち 2 件を試み、11 要求で停止した。
旧方式の図書予約切替は 8 要求で達成したが、現在根拠方式は 3 要求目、2 判断目の評価で HTTP 400 `max_tokens_exceeded` となった。
残る 16 件と OpenAI Responses の呼び出しは未実行で、三方式の性能比較は成立していない。

失敗した評価と旧方式の同じ画面では、モデル入力、添付画像、役割以外の質問が完全一致した。
役割を含む質問は 42 問、61,060 バイトから 47 問、73,852 バイトへ増えていた。
公式の[文脈上限](https://docs.typesafe.ai/models)と[エラー仕様](https://docs.typesafe.ai/api/errors)では、長文脈ヘッダーでも上限があり、`max_tokens_exceeded` は文脈超過を表す。
失敗時の正確なトークン数は取得できていない。

現在根拠方式の繰り返し説明を短くし、選択肢、画像、根拠制限、質問数、行動方策を維持する。
旧方式の質問は変更しない。
したがって修正後の比較では、根拠制限と短い指示文を組み合わせた設定として評価し、結果の差を根拠制限だけの効果とは扱わない。
各質問は独立した判断として読める説明を持たせ、別の質問の回答を暗黙に参照させない。

初回の 45 原本を含め、最初の修正時点では 4,642 ファイルを `prior-raw-v2.json` で保全した。
修正後の実行は別の新規ディレクトリと台帳で予定 18 件、最大 504 要求とし、初回 11 要求も累計に含める。

## 画像参照名の衝突

質問数を戻した producer `69f74a58362eada271e423438c1e3fa3dcbf679d` も 2 / 18 試行、11 要求で同じエラーになった。
三度の実行は計 33 要求（HTTP 成功 30、失敗 3）で、Responses はまだ到達していない。
質問数や UTF-8 バイト数だけでは、実際に展開される画像入力を説明できていなかった。

[公式の画像参照仕様](https://docs.typesafe.ai/images)では、asset の参照名が文字列内に現れるたび、その部分を画像に置換する。
従来は短い名前 `current` を使用していたため、操作説明や `delivered-current-view-only` などの文まで画像へ展開されていた。
第 2 評価の同じ画面では、この名前の出現数は旧方式 58、新方式 94。
最初の評価では新方式の文が短くても、報告入力トークン数は旧 85,281、新 109,177 と増えていた。
未取得の失敗トークン数や provider 内部の正確な展開サイズは推定値で埋めない。

送信境界でのみ、画像ごと・要求ごとの新しい UUID に参照を変更する。
置換するのは観察、観察記憶、阻害理由、候補対応、レビューの明示された画像フィールドだけである。
目的、ペルソナ、自然文、質問、選択肢、元の論理入力、画像バイト列は変えない。
通常の文字列で UUID が衝突する場合、不明な画像や未使用 asset がある場合は、送信せず失敗として扱う。
実際の UUID、画像ハッシュ、対応する論理名とフィールド位置は `request.imageBindings` に保存する。
成功・通信失敗の双方で記録し、リプレイでは元の入力と対応表の整合を検証する。
この表は監査用で、モデル入力へ再挿入しない。

この送信修正は三方式へ共通適用する。旧方式も方策・質問は維持するが、過去版の偶発的な画像複製はなくなる。
したがって過去版との数値差を今回の意味表現だけの効果として扱わない。
同じ画像を複数の明示フィールドから参照する既存構造は残し、画像の出現数は UUID とパスから追跡する。
三度の停止の 135 原本も含む 4,732 ファイルを `prior-raw-v4.json` で保全する。
次の新規比較は 18 試行・最大 504 要求で、既実行 33 要求を含め最大 537 要求とする。


独立検証では、opaque-v1 の宣言がある記録でも、応答モデル名を変更すると画像対応表の欠落を見逃す P2 を 3 通りで再現した。
モデル名にかかわらず、宣言済み方式の全応答へ対応表を要求するように修正し、同じ改ざんで再検証する。
既存 8 ファイルの回帰実行は 53 件中 49 成功、4 失敗として保存した。
うち 3 件は新しい安全な通信記録の追加に対する古い期待値であり、元記録を変更せず厳密な対応表検査へ更新したオフライン再検証 5 / 5 が通った。
残る 1 件は過去 b7 版のソース全文と現在実装の一致を要求する既知の検査で、テスト本体と失敗証拠は変更していない。
全体スイート成功とは扱わず、今回の変更に関する検証結果を個別に示す。


## UUID 送信の実行結果と条件付きスキーマ

UUID 版 producer `d6796fca744ee3b9b33f075d45eb2eda4432339f` は 3 / 18 試行、17 要求で停止した。
旧方式と現在根拠方式の最初の図書予約課題は、各 8 要求で達成した。
既知の失敗地点である 2 判断目の評価は、旧方式が 199,918 から 29,917 入力トークンへ減り、現在根拠方式も 28,046 トークンで通過した。
同じ文字列や質問数でも、参照名による画像複製を除くことが必要だった。
この 2 件だけで、他の課題全般の安定性や探索性能を結論しない。

3 試行目の Responses は HTTP 200、`gpt-6-luna`、入力 2,123・出力 730 トークンで応答した。
しかし条件 `c3` は `status: "unmet"`、`evidence: null` であり、既存の受理条件が拒否した。
JSON 生成と API 接続は成立したが、抽出仮説の受理、Jev への追加情報の引き渡し、三方式の性能比較は未成立である。
残る 15 試行は未実行で、これを離脱や操作失敗へ算入しない。

送信スキーマはこの組合せを許しており、ローカルの根拠条件との間に差があった。
次版の `evidence-conditional-v1` は、[公式に対応する入れ子の anyOf](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)で既存条件を表現する。
条件が `satisfied` または `unmet` なら引用根拠を必須とし、根拠がなければ `uncertain` とする。
既知の操作関係、または操作後の確認予測には、現在画像の引用を必須とする。
受理処理、画像・候補・記憶の制約、引用の未検証マーカー、通信失敗と不正出力の区分は変えない。
引用が存在しても、転記や意味解釈が正しいとは限らない。

新しい比較計画は抽出方式から開始し、その後も三方式の順序を均等に回す（`actorOrderOffset: 2`）。
形式の不整合を先に検出するための事前変更であり、停止した試行の置換や再試行は行わない。
三方式・6 条件・各 1 回の 18 試行、最大 504 要求は維持する。
既実行は 50 要求（Jev 49、Responses 1）で、次版との合計上限は 554 要求。
旧 4 実行の 201 原本も含む 4,798 ファイルを `prior-raw-v5.json` で保全する。
