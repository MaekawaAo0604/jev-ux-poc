# 1. 今回の目的

今回確認したいのは、次の一連の処理が実Jevで成立するかです。

「目的に必要な情報が現在の注視領域では取得できない」
→「別の場所を見る」
→「新しい情報を取得する」
→「その情報が次の判断・操作に反映される」

そのうえで、同じ機能のUIについて、配置や文言を個別に変更したとき、観察・判断・操作がどう変わるかを比較できる状態にしてください。

目的は、タスク成功率を無条件に上げることではありません。

- 実装の不具合
- 視覚・認識・状態管理・行動選択の不足
- 設定した予算や上限による打ち切り
- ユーザーシミュレーション上の行動

これらを切り分け、必要な部分だけ改善することが目的です。

人間との一致度、性能上の有意差、一般的な製品への適用可能性は、今回の疎通や少数試行だけで実証したと扱わないでください。

## サブA：探索上の問題の切り分けと最小修正

以下を区別して分析してください。

- 必要な領域へ注視が移らない
- 注視しても文字や対象を認識できない
- 認識できる情報が状態へ渡らない
- 過去に取得した情報が不適切に消える、または漏れる
- 候補生成や分布処理が不適切
- 実行器が選択された操作を正しく実行していない
- 完了判断と客観的結果の接続が不適切
- 正常な確率的選択や自主的離脱
- 予算・時間・操作上限による打ち切り

修正する場合は、原因の証拠を示したうえで最小限にしてください。
再現テストまたは回帰テストを追加してください。

禁止する修正：

- 成功させるために正解の場所や手順をモデルへ渡す
- 視覚制約を黙って外す
- 見えない文字をDOMや候補ラベルから渡す
- samplingを黙って最大確率選択へ変える
- 失敗や離脱を成功へ読み替える
- 同じ場所を再訪しただけで、無条件に不具合扱いする
- API_LIMITを避けるためだけに終了判定を緩める

問題が確認できなければ、無理に製品コードを変更しないでください。
未確定の仮説と、確認するための最小実験を返してください。

## サブB：同機能の比較UIと検証テスト

通知停止の機能と客観的成功判定を維持し、次の3種類を用意してください。

A. reference
   基準となるUI。

B. position-only
   対象要素の位置だけを変更する。
   文言・色・機能・初期状態は可能な限り固定する。

C. wording-only
   対象要素の文言だけを変更する。
   位置・色・機能・初期状態は固定する。
   文言は同じ操作意図を表すものとし、機能自体を変えない。

配置変更は、まず同一viewport内で比較できるものにしてください。
スクロールの必要性や画面サイズまで同時に変えないでください。

各UIについて以下を確認してください。

- 通常操作で目的を達成できる
- 同じ意味の客観的成功判定が動く
- 試行ごとに初期化できる
- UI版と変更箇所が記録される
- モデル入力に「良いUI」「悪いUI」「正解位置」等の答えを漏らさない

同じUI版の条件間では初期fingerprintの一致を確認してください。
異なるUI版同士は意図的に見た目が違うため、画像fingerprintの一致を要求しないでください。
その代わり、機能・データ・初期状態・意図した差分を確認してください。

この3種類を、人間にとって良い／悪いと事前に断定しないでください。
確認するのは、変更に対して観察と行動がどう変わるかです。
