# 一時保留方策の独立受入確認（2026-10-28）

独立検証担当は、一時保留方策の実装と、保存済みの実モデル比較を受け入れた。
製品ロジックの実装に参加していないコンテキストでコードを読み、実アダプター、実ラッパー、ローカルブラウザーを通す試験と、実モデル試行の保存監査を行った。
受入範囲に対する修正必須の指摘はない。

検証した製品版は `5abeef326a4f20bb9962aad6a3f34e7b5c5d851f`、ソース集合の SHA-256 は `924cd64d79756f4e4c6b85eb71e40abf879e1c10b29c9564e01dede2b0c3f113` である。
両実モデル試行の manifest、result、新台帳と、監査時の製品ソースが一致した。
独立検証担当は製品コード、実環境ファイル、人間の記録に触れず、実 API 要求を行っていない。
祖先の `AGENTS.md` と計画、プロトコル、Charter を確認したが、祖先の `.codex/AGENTS.md` が参照する 12 個の追加 Markdown は存在しなかった。

独立試験は最終版を 6 件実行し、すべて通過した。
別途、保留モジュールと sampler/state の関連 35 件が通過し、親の旧回帰ログ 117 件の通過も確認した。
35 件には親の検証との重複があるため、独立な新規ケース数には加算しない。
型検査も通過した。
試験と根拠は [検証コード](../../tests/temporary-deferral-independent.test.ts)、[受入メモ](../../reports/temporary-deferral-2026-10-28/independent-preflight.json)、[最終実行ログ](../../reports/temporary-deferral-2026-10-28/independent-preflight-final-all.log) に保存した。

実 API を fetch スタブに置き換えた試験では、次を確かめた。

- 画像が一致する実クリックの帰還経路から、画像ハッシュと候補 ID に対応した保留を作る。補正後の候補を実行し、次の画面が別の入口の遷移先であることを確かめる。
- 有望な別入口も保留になった後に、全重みを 1 に戻して元の入口を再訪する。全候補を残し、元の正確率を 0 にせず、done と非クリック候補の重みを変えない。
- 根拠付きの正進展を含む帰還と、根拠を受理していない非進展では、画像が一致していても保留しない。
- 安全上の除外を補正で復活させず、seed から選択を再生する。不正な重みは選択回数を進めずに拒否する。
- 不正分布は `INVALID_DISTRIBUTION`、HTTP 503 は `API_ERROR` として終了し、利用者の断念として記録しない。
- 保留の候補、証拠ハッシュ、理由、選択重み、判断重みの改ざんを、経験からの再構築で拒否する。既存の baseline、deliberation、experience-basis の実保存物も再生できる。

モデルへの入力分離は、同じ wait→done の経路を通る fresh context の control と treatment で確認した。
各条件 4 要求の gateway body 全体が、画像の base64、全状態、質問、ハッシュを含めて一致した。
この試験では画面やハッシュを差し替えていない。
実モデル比較では条件ごとの応答と経路が変わるため、この一致を両試行の全経路へ一般化しない。

実モデル比較の保存監査では、対照が 24 要求、12 判断で判断上限に達し、独立目的判定は未達だった。
保留ありは 14 要求、7 判断で主観的完了に達し、独立目的判定も達成した。
最終画像には「現在の設定：停止」と「メール通知を停止しました」が表示されている。
両試行の初期画像と最初の番号付き入力画像は一致し、設定差は条件 ID と保留設定だけだった。
旧 8 台帳は事前の SHA-256 とバイト単位で一致し、新規の実要求は合計 38/48、送信試行は各要求 1 回、追加レビュー要求は 0 だった。
両試行を API なしで再生できた。

保留ありの第 4 判断では、モデルの生分布の最大候補は「各種設定」の e4=0.91 だった。
モデル自身は、その前のキャンペーン画面 o3 を根拠に「進展なし」「予想不支持」と評価していた。
3 回の実クリックでホームの同じ画像へ戻り、根拠付きの正進展がなかったため、方策が e4 に 0.01 を掛けた。
補正後は e4 が約 0.09183、「その他」の e5 と下スクロールがともに約 0.40363 となった。
sampler は候補キー順の argmax で同率を解決し、e5 を実行して `#other` へ移動した。
その後は「お知らせの管理」へ進み、メール通知を停止して完了した。
したがって、この判断では保留補正が実際の入口を変えたが、「その他」を一意に優先した分布ではなかった。
キャンペーン画面の e2 と e3 はどちらもホームへ戻るため、その候補 ID の違いを課題の分岐回復には数えていない。
全候補を保留した後の解除は実モデル試行では観測しておらず、実ブラウザーを使うスタブ試験で確認した。

初回の独立試験では、ブラウザーの「戻る」で同じ画像へ戻ると仮定した 2 ケースが失敗した。
画素比較では、初期ホームと帰還後の差が e4 タイル内の 31,829 画素に限られ、表示画像でも hover による背景と枠の変化を確認した。
差分の範囲は x=610..904、y=540..653 だった。
CSS には hover と 0.15 秒の遷移があり、残ったマウス位置による表示差で画像ハッシュが変わっていた。
スクロールや候補一覧の変化が原因という初期推測は撤回した。
初回ログを保存したまま、入力一致には静止した wait→done、保留と解除には画面内のホームリンクを使う実経路を用い、同じ画像という前提を実際に検査した。

1 条件 1 試行の順序固定比較から、一般的な改善率、因果効果、人間行動の再現性は算定していない。
生応答は保留が発火する前から条件間で異なり、保存した第 4 判断の補正前後の比較だけが局所的な選択変更の根拠となる。
モデルによる意味判断、重み 0.01、有望さの閾値 0.01 は未較正であり、hover、アニメーション、スクロールによる画像差で保留が対応しない場合がある。
再生は画像、分布、経験と保留の再構築を検査するが、UI 操作の再実行や、保存物すべてを整合的に置換する改ざんの検出までは行わない。
