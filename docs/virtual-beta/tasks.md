# 仮想βテスト：実装・追加調査タスク

作成日：2026-10-27（JST）

[目的・実装差分](README.md) / [確認済みの研究・実装候補](research.md)

## 実装担当への前提

目標は、公開前のプロダクトに対して、対象ユーザー集団の探索・認知・体験・行動・離脱と、設計変更の影響を検証できる仮想βテストを作ること。

以下は未着手を表すバックログであり、実装済みの報告ではない。既存の作業版を確認し、重複しているものは根拠を付けて完了または一部完了へ変更する。

- 学術的新規性の追求や、現在のPoCの即時販売を作業目標にしない。
- 全てを一度に実装しない。部品の追加が何に効いたか比較できるようにする。
- 既存の操作成功を目指すモードを壊さず、人間再現用モードを分ける。
- API失敗や実行基盤の不具合を、ユーザーの迷い・離脱として数えない。
- 実際に調べた事実、実装案、仮説、未確認事項を区別する。
- 人間のデータが存在しない箇所を、AIで生成した「人間データ」で埋めない。
- 性能確認前に「人間を再現した」「離脱率を予測できる」と結論しない。

## T00. 最新実装と実験成果の所在を確定する

### 不足

GitHubの確認スナップショットと、画像入力・ペルソナ比較を行っている作業版の対応関係。

### 作業

- [ ] 作業ツリー、ブランチ、コミット、未push変更を確認する。未コミット変更を上書きしない。
- [ ] 画像が実際にモデルへ送られる経路を、入力直前のコード・ログで特定する。
- [ ] Persona/Charter、確率ログ、理由説明、LOOP判定、画像認識の既存実装と実験結果を棚卸しする。
- [ ] 過去のLOOP問題について、既に修正済みか、基盤・認識・判断・終了条件のどこが原因かを既存記録で確認する。
- [ ] 現在の実行コマンド、モデルID、API経路、パラメーター、利用できる保存済み結果を整理する。

### 成果物・完了条件

`implementation-inventory.md`等に、機能・実装場所・状態・証拠・基準コミットを記載する。状態は「実装確認済み／性能未検証／未確認／追加が必要」に分ける。以降のTODOを、この棚卸しに基づき修正できること。

## T01. 観察・ユーザー状態・行動・監査を分離する

### 不足

実際の画面や内部状態と、仮想ユーザーが知り得た内容を区別する契約。

### 作業

- [ ] `UserSpec`：安定した知識・経験・目的に対する傾向・利用制約を定義する。
- [ ] `Charter`：目的、初期条件、対象範囲、禁止操作を定義する。正解の操作順は入れない。
- [ ] `Observation`：実際にユーザー側へ渡した画像・文字・時刻・座標を保存する。
- [ ] `UserState`：注視位置、認識・誤解、期待、参照可能な記憶、仮説的な感性状態を持つ。
- [ ] `DecisionPolicy`：状態と候補から分布を返す部分と、その分布から実行行動を選ぶ部分を分ける。
- [ ] `ExecutionAudit`：操作結果、内部の成功判定、通信障害、環境の状態を記録する。エージェント入力と別管理する。
- [ ] `task-solver`と`user-simulator`を設定で切り替え、探索候補の除外・再訪制約・成功停止の違いを記録する。

### 成果物・完了条件

型またはJSON Schemaと最小の実行例。監査専用の情報がユーザー側の入力へ漏れないテストがあること。既存の実行方式を維持できること。上記名称・配置は提案であり、既存型があれば拡張する。

## T02. 部品ごとの比較と再現性を確保する

### 作業

- [ ] UI版、画面サイズ、端末条件、初期データ、ペルソナ、タスク、候補順、モデル、プロンプト、サンプラー設定を記録する。
- [ ] UIとブラウザー状態を初期化できる小さな比較環境を作る。
- [ ] 同一の人物特性を固定し、試行ごとの偶然性だけを変える設定を持つ。
- [ ] サンプラーのseedを保存する。API出力自体が完全再現できるとは扱わず、レスポンス保存による判断リプレイも用意する。
- [ ] DOMベース、全画面画像、切り取り、注視領域＋周辺ブラーを別条件として保存する。
- [ ] 視線方式の比較中にペルソナ、選択方法、探索制約まで同時変更しない。
- [ ] 画面のGood/Badという名前や正解経路を、判断入力に漏らさない。

### 成果物・完了条件

比較設定、再実行コマンド、実行ID別のログ。部品を一つ変更した差と、実行ごとのばらつきを分離して報告できる。試行数は目的と観測分散から決め、少数の配線確認を性能実証として扱わない。

## T03. 注視領域と周辺視の入力制約を実装する

参照：[S04〜S06、S11](research.md)。

### 作業

- [ ] `full-frame`、`crop-only`、`foveated`を同じ入力アダプターで切り替える。
- [ ] 注視点、鮮明領域の大きさ、周辺の劣化方法、画像リサイズ、viewportと画像の座標変換を記録する。
- [ ] 周辺の情報を全消去する方式と、大まかな色・形・配置を残す方式を区別する。
- [ ] 視野制約後の画像をモデルへ送る。加工前画像は監査専用とする。
- [ ] DOM全文、候補ラベル、alt属性、アクセシビリティツリー等から、画像で見えない意味が漏れる経路を調べる。
- [ ] 観察可能性の制御を、行動候補の提示にも反映する。DOMは操作先の解決に利用しても、その意味を無条件に判断へ渡さない。
- [ ] あらかじめ周辺だけに配置した文字・目標情報で、入力経路の漏洩テストを作る。

### 成果物・完了条件

加工前後画像、設定、実際の送信入力を追えること。解像度を落としただけで「人間の見え方を再現した」とはしない。鮮明領域のサイズ等は仮パラメーターと明示し、人間データに合わせる必要性を残す。

## T04. 視線移動と動的な注意を別アクションにする

### 作業

- [ ] `look(x,y)`とclickを分離する。必要なら全体を粗く見る操作も追加する。
- [ ] 注視だけでUIを操作しないこと、座標系がズレないことをテストする。
- [ ] 注視履歴を持ち、次の観察先の候補と分布を記録する。
- [ ] 注意選択モデルを差し替え可能にし、全画面一括認識・単純な走査・顕著性ベース等を比較対象にする。
- [ ] 連続画像の差分から動き・点滅・表示変化の候補を取得する。スクロールやページ全体の移動と局所的な変化を区別する。
- [ ] 動きを検出したら必ず見る、という固定ルールにはせず、目的・履歴・特性を含む選択として比較する。
- [ ] フレーム取得間隔は設定値とし、取りこぼし・処理量・認識への影響を検証する。

### 成果物・完了条件

注視列とUI操作列を別々に再生できること。動きのある／ない同等のUIで比較できること。「実行処理にかかった秒数」と「利用者のモデル上の経過時間」を分離する。

## T05. ユーザー仕様書を、利用中に変化する状態へ接続する

参照：[S01、S07](research.md)。

### 作業

- [ ] 安定した個体特性と、操作のたびに変化する状態を分ける。
- [ ] 「画面に存在する」「視界に入った」「注意を向けた」「理解した」を別の状態として表現する。
- [ ] 知らない用語、誤解した意味、期待した結果、失敗経験、参照できる記憶を更新する。
- [ ] 全履歴は監査用に残しつつ、判断入力にはそのユーザーが利用できる情報だけを渡す方式を比較する。
- [ ] 信頼・負担感・不安等の状態を使う場合、定義と観測可能な対応指標を先に決める。
- [ ] 感性スコアはモデルの予測値として記録し、人間の感情の実測値と混同しない。
- [ ] 専門知識を与えない条件で専門用語を理解してしまう等、設定への不整合を集計する。

### 成果物・完了条件

同じ個体の状態遷移を追えること。ペルソナの説明文が変わっただけでなく、観察・選択・結果にどう影響したか比較できること。最初から脳全体のモデルを作るのではなく、追加した状態ごとの効果を確認する。

## T06. 行動確率の意味とサンプリングを実装・検証する

参照：[S11](research.md#s11-typesafejev公式仕様)。

### 作業

- [ ] 現行の最大確率選択を残し、分布からのサンプリングを独立した方式として追加する。
- [ ] 問いを「正解・最適操作」から「この条件の利用者が選びそうな行動」へ変更した条件を比較する。
- [ ] クリック以外に、読む、見直す、待つ、戻る、諦める等が必要か検討する。
- [ ] 不正な確率、候補欠損、負値、総和の異常を検出し、黙って成功扱いにしない。
- [ ] モデル分布、校正後分布、安全フィルタ後分布、選択行動、seedを保存する。
- [ ] 安全フィルタで行動が除外されたら、変更内容と終了理由を保存する。安全制約による停止を自然な離脱率に含めない。
- [ ] 理由を出す場合は短い説明と画面上の根拠を記録する。説明文を真の内部判断過程とみなさない。
- [ ] 観察→状態更新→行動判断を、独立質問の同時呼び出しだけで依存関係が成立したことにしない。

### 成果物・完了条件

保存済み分布とseedから選択を再現できること。最大確率選択との比較結果が出ること。人間データがない段階の成果は「確率的実行が成立した」までとし、「人間の確率を再現した」とはしない。

## T07. 人間との比較・校正・未見条件での評価

### 作業

- [ ] 人間側とJev側で、UI版・目的・利用条件・初期状態・利用可能な情報を対応付ける。
- [ ] 公開データで評価できる項目と、独自取得が必要な項目を分ける。
- [ ] 操作ログ、視線、主観評価を混同しない。カーソル位置だけから注視を断定しない。
- [ ] ユーザー属性だけでなく、知識・経験・目的に関連する条件を記録する。
- [ ] 調整用と評価用をユーザー・画面・タスク等の単位で分離する。独立性を壊す重複を確認する。
- [ ] UI変更の前後を比較する。人間側の繰り返しで学習効果が出る場合、別集団や順序の調整を検討する。
- [ ] 同一条件内のばらつき、条件間の差、母集団への予測誤差を分けて出す。
- [ ] 信頼区間の単位を明記し、同じ仮想個体の繰り返しを独立した実ユーザー数として数えない。
- [ ] どの誤差・条件で予測を保留するか決める。合否の閾値は結果を見てから都合よく変更しない。

### 指標の候補

| 対象 | 指標候補 | 注意 |
|---|---|---|
| 視覚的注意 | 要素の発見率、最初に見る領域、注視順、再注視 | 視線が一致しても理解まで証明されない |
| 行動 | 選択頻度、誤操作、再訪、目的達成、離脱 | 基盤障害と安全停止は別集計 |
| 確率 | 人間の選択に対するBrier score等、確率帯別の実測頻度 | 人間データへの評価であり、AI同士の一致ではない |
| 体験 | 同じ尺度で取得した主観評価との差 | AIの自己申告を人間評価として使わない |
| 設計変更 | 改善・悪化の方向、変化量の誤差、集団別の差 | 全画面評価・多数派固定等の単純基準とも比較 |

### 成果物・完了条件

評価計画と比較データの仕様。実験後には「どの条件で何をどの精度で予測できたか」「未評価の範囲」を報告する。必要な試行数はパイロットの分散と検出したい差から設計する。個人データ・画面・認証情報を公開リポジトリに保存しない。

## T08. 仮想個体の集団と継続利用を扱う

### 作業

- [ ] 対象集団の目的・経験・端末・状況等の構成を定義する。
- [ ] 属性を独立にランダム化するだけでなく、組み合わせの根拠を保持する。
- [ ] 個人ごとの安定した特性、個人内の偶然性、モデル自体の不確実性を分ける。
- [ ] 実測がない属性分布は仮説とし、分布を変えたときに結論が変わるか確認する。
- [ ] 初回と再訪を区別し、同じ個体の記憶と経験を維持できるようにする。
- [ ] 数週間の継続利用を扱う場合、時間を進めるだけではなく、利用契機・外部状況を何としてモデル化するか決める。

### 成果物・完了条件

集団構成と生成根拠を再現できる設定、属性別の結果、分布を変えた感度分析。単に人数を増やすことで代表性や長期予測が成立したとは結論しない。

## T09. 大規模実行と対象操作を拡張する

### 作業

- [ ] UI上のフォーム入力、select、キーボード、エラー回復等の必要操作を棚卸しする。現在の作業版で既に対応しているものは流用する。
- [ ] 個体ごとのブラウザー・アカウント・データを分離する。サーバー側データの共有による汚染も確認する。
- [ ] キュー、並列数、レート制御、リトライ、中断再開を実装する。
- [ ] 操作の重複実行を防ぎ、基盤エラー率を独立して可視化する。
- [ ] 各実行の入力・出力・モデル・UI版・設定を固定して追跡できるようにする。
- [ ] API待機時間、ブラウザー処理時間、ユーザー行動モデル上の時間を分離する。
- [ ] 多数アクセスによるサービスの遅延を、UXの認知モデルの失敗と混ぜない。負荷試験は別の実験条件として扱う。
- [ ] 実注文、金銭移動、外部送信を行わない検証環境を用意する。

### 成果物・完了条件

個体数を段階的に増やした実行結果と、処理量・失敗率・再現性の報告。大規模実行の成立と人間再現の成立は別々に記載する。

## T10. UX評価から設計改善へつなぐ

### 作業

- [ ] 問題候補を、画面・観察・行動・ユーザー条件・結果へ結び付ける。
- [ ] 観測事実、原因仮説、改善案、未確認事項を分けて出力する。
- [ ] 設計変更をバージョンとして管理し、元と変更後を同等条件の個体集団で比較する。
- [ ] 次の一操作だけでなく、セッション結果と他ペルソナへの影響も再評価する。
- [ ] 開発AIには改善案を渡しても、評価用の未見データや正解ラベルを漏らさない。
- [ ] 変更案を繰り返し評価する際の過適合を防ぐため、最終判定用の条件を保持する。
- [ ] 新たな障害・性能悪化・安全上の問題を通常のテスト系で監査する。
- [ ] 自動改善は安全なブランチ／検証環境で行い、根拠と差分を残す。停止条件、保留、ロールバックを用意する。

### 成果物・完了条件

変更前後の結果、根拠付きの改善判断、悪化した集団の有無を追えること。UIが評価AIに適合しただけなのか、人間の結果を改善できているかをT07の評価系で確認する。

## 追加調査のチケット

### R01：視覚制約と注意モデル

- **問い**：注視画像の加工と、次に見る位置の選択に、どの既存部品を使えるか。
- **対象**：UEyes、MODG、視野制約下の注視学習研究。目的付きWeb操作・動的注意に対応する追加候補。
- **確認**：コード、重み、データ、座標系、目的条件、履歴、個人差、学習の必要性、利用条件。
- **成果物**：「そのまま利用／ラッパーで利用／追加学習／自作／採用保留」の比較表と根拠。
- **完了条件**：T03・T04で最初に試す構成と、比較相手を決められる。

### R02：人間の比較データ

- **問い**：既存データで測れるものと、自分たちで取得する必要があるものは何か。
- **確認**：静止画／連続操作、自由観察／目的付き、視線座標・時刻、操作、主観評価、ユーザー条件、再配布・学習利用の条件。
- **成果物**：データセットの対応表と、不足分の取得プロトコル。データの修正版や版番号も記録する。
- **完了条件**：T07の各指標について、比較データの調達経路が分かる。

### R03：Jevの確率・画像入力・接続方式

- **問い**：現在使うAPI経路で何が入力・出力でき、行動分布として何を補う必要があるか。
- **確認**：モデルID、画像入力形式と制約、リサイズ、座標取得、Choice、確率、confidence、失敗時の応答、独立質問の実行特性。
- **成果物**：固定したモデル／経路での最小入出力例と、既存クライアントとの差分。
- **完了条件**：画像の観察、状態更新、分布出力、サンプリングの接続方法が決まる。人間行動との一致は別に評価する。

### R04：認知・記憶・感性の測定とモデル化

- **問い**：どの状態を追加すると、対象とする体験と行動を説明・予測できるか。
- **確認**：感性工学・主観評価の既存尺度、知識・期待・信頼・負担の測定、時間変化、状態から行動への接続、取得負担。
- **成果物**：状態の定義、観測可能な指標、更新仮説、比較実験の対応表。
- **完了条件**：T05で追加する最小限の状態と、不要なら削除できる比較方法が決まる。感性の名称や数値を増やすだけで完了にしない。

### R05：実行基盤と公開実装の流用

- **問い**：本リポジトリを維持しながら、どの部品の自作を減らせるか。
- **対象**：UXAgent等の実行設定・ログ・並列化、MODGの観察ハーネス。
- **確認**：固定コミットでの起動、依存関係、ライセンス、データ・重みの別条件、TypeScriptからの接続方法。
- **成果物**：流用単位と接続案、既存実装と重複する機能、起動できなかった理由。
- **完了条件**：利用する部品と、自分たちで維持する部品の境界が決まる。

### R06：母集団と再訪・長期利用

- **問い**：実ユーザーログがない段階で、集団構成と継続利用をどこまで設定・検証できるか。
- **確認**：既存調査や類似領域データの適用範囲、属性の相関、初回と再訪、外部状況、代表性、不確実性。
- **成果物**：根拠のある設定と仮説設定の分離、複数の集団構成による感度分析案。
- **完了条件**：対象範囲と、根拠が足りず予測を保留する範囲が明確になる。
