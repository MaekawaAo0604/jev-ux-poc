# Jev の画像入力を使った探索

2026 年 10 月 16 日に、既存の探索処理へスクリーンショット入力を追加した。
操作候補の抽出、Playwright による実行、Action Trace の記録、回帰テストの生成は既存の処理を使う。
`--vision` を付けた試行では、判断直前に保存した PNG のバイト列を Jev に渡す。
API の再試行時は画面画像も比較し、画像だけが変わった場合も観測からやり直す。

## 2026 年 10 月 18 日の本番統合

`--vision` の既定を、番号付きの現在画像と OCR なしの操作選択へ変更した。
公開サイト用とローカル用は `AccountPage.captureDecisionScreenshot` と `pages/visual-numbering.ts` を共用する。

## 実行方法

### 画像由来の判断記録を渡す

`--vision --image-only --image-memory` は、画像専用の入力分離を維持しながら、以前の画像を見た Jev の Choice 判断を次の判断に渡す。
記憶なしの `--vision --image-only` は比較用に残した。
公開サイトとローカルの CLI の両方で指定でき、`--image-only` がない場合は拒否する。

`jev/image-judgments.ts` は、Goal 原文の断片について `observed`、`not_shown`、`context`、`contradicted`、`uncertain` の判断を保存する。
各記録にはステップ、匿名ページ ID、実際に送信した PNG の SHA-256、モデル名を残す。
`not_shown` は以前の根拠を否定しない。一方、`contradicted` と `uncertain` は以前の確認状態を保留に戻す。
背景・制約だけという `context` 分類もモデル判断であり、Goal の要求を省略してよいという意味ではない。
分割は句読点と一部の接続表現によるもので、文意の完全な分解ではない。
同じ原文断片に複数の要求が残る場合、その項目内の情報を別々には保持できない制約がある。

全更新は保存ログに残すが、次の判断には各項目の現在の状態、その状態を確定した最新の出典、更新回数を渡す。
送信形式は `representation: current-state-and-latest-source` で区別する。
後の `not_shown` は確認元を更新しないため、以前の `observed` の出典を保つ。
件数で打ち切る処理ではなく、状態の更新規則に沿った集約であり、取消や不明を過去の確認で上書きしない。

入口は現在画像に対応する未探索のクリック先だけを判定し、既存の探索対象 ID に `promising`、`unrelated`、`uncertain` と画像出典を保存する。
画面外の入口を現在画像だけで再判定せず、以前の画像から得た判断と出典を渡す。
入口の見込みは Goal 達成の証拠とは扱わない。
入力は許可した項目から組み直し、DOM の本文・ラベル・URL を戻さない。

判断用の追加質問は、その画面の最初の操作判断にまとめて送る。
同じ画面の完了再確認や別ルート選択で同じ判断を重ねて保存しない。
返答全体の検証を終える前には記録を確定せず、再試行中の画面変化や不正な返答で一部だけが残らないようにする。
元の Goal 全体に対する独立した Choice 照合と、判断記録の未確認項目チェックを両方通過した場合だけ完了を認める。
操作目的は、以前に成立したという記録だけでなく、最新画像で結果が成立していることも照合する。

このモードでは、一次判断が許可済みの経由操作を選んだ場合、その移動を情報の少ない二次選択で停止へ上書きしない。
確定済みの別ルートがある場合は従来の継続を優先し、既探索の除外と Playwright 側の安全確認を維持する。
`navigationTransit` は可能な対象 ID を記録するもので、対象を選択・到達したという記録ではない。
継続経路がない場合は、その一次操作を最初の移動として持つ既知・未探索先のうち、移動回数が最少の対象をコード側で確定する。
その対象を `frontier.selectionSource: current-transit` として既存の経路継続へ渡し、実操作を終えてから探索済みにする。
これは経路構造からの選択であり、Jev が対象の意味や有用さを判断した記録ではない。


### 完了照合と Back の修正

確認項目が揃った時点でも、一次判断の `done` を待たずに全 Goal を照合するよう変更した。
この照合が `complete` で、照合後も画像由来の確認項目が揃っている場合だけ終了する。
`incomplete` と `uncertain` なら一次判断の操作を維持し、従来の経路継続へ進む。
`completionCheck` には元の一次判断、照合の生返答、未確認項目、起動理由を残す。
起動理由は `primary-done` または `image-evidence` であり、照合から終了した場合に一次判断の確率を捏造しない。

Back の失敗は、前回停止した実サイトの 2 ページだけを Jev なしで再現して調べた。
ブラウザの履歴位置は承認済みの前の ID に移っていたが、表示 URL は出発地点のままだった。
2 回目の診断では、停止判定の約 19 ミリ秒後に正しい戻り先への `framenavigated` が発生した。
ローカルでも、`beforeunload` 内の同一 URL への `replaceState` と遅い応答で同じ失敗を再現した。

`goBack` の後で、承認済み URL の `DOMContentLoaded` を待ち、続いて従来の履歴 ID と URL の照合を行うよう修正した。
固定時間の待機や未知の戻り先の許可は追加していない。
誤った URL に書き換わる着地は引き続き拒否する。
実サイトの修正後の診断は `reports/back-probe-2026-10-17T20-02-55.855Z/diagnostic.json` に保存し、正しい URL と履歴 ID への復帰を確認した。

終了画面の撮影失敗は `finalCapture.status: ERROR` として、探索の終了理由とは分けて記録する。
公開サイト用とローカル用の両方で、終了理由と実行済み Action Trace を保持する。
撮影の例外メッセージは `finalCapture.error` に残すが、判断 API の生エラーを保存する変更ではない。
撮影に失敗した試行はサイトの UX 指標に数えない。

### 判断記録だけでは残る制約

探索とは別に、最後の `observed` の出典 2 枚と終了画像だけを、既存の画像監査へ渡した。
49 画面すべては送らず、DOM、OCR、回答文も追加していない。

記録は `reports/memory-evidence-audit-2026-10-17T20-15-57.661Z/audit.json` に残した。
元の探索結果は変更していない。

ただし、現在の記録が「確認済み」という判断と出典だけで、回答内容を保持しないことは実装上の制約である。
「必要か」と「不要か」の回答内容は、同じ `observed` だけからは復元できない。
今の状態だけで、複数画面の Goal の完了判定を解決したとは扱わない。

### 完了照合だけに出典画像を追加する

上の診断後、承認された方式を `--image-memory-proof` として実装した。
`--vision --image-only --image-memory` に追加し、公開サイト用とローカル用の両方で利用できる。
従来の比較用モードは変更していない。

操作判断には現在画像 1 枚だけを送る。
`completionCoverage` に限り、現在の各 `observed` 項目を確定した最新の出典画像を保存 PNG から読み込み、実際の送信時に記録した SHA-256 と照合して追加する。
同じ出典と現在画像の重複は除く。
取消・不明・背景だけの項目や入口の見込みは、根拠画像の選択に使わない。
画像が欠落・改変した場合は送信前に停止し、根拠を省略して完了扱いにしない。
選択した出典、照合状態、画像数は各要求の `completionProof` に残す。
画面をまたいで保持するのは出典メタデータであり、全画像のバイト列ではない。

制御した画像列を実際の Playwright で撮影し、Jev へ渡した。
この検証は移動能力の試験ではなく、画面をまたぐ完了照合を切り分けるもので、検証コードが観測画面を切り替える。
料金と受付時間を別画像で示し、その後に一覧画面へ移した場合は、現在画像と出典 2 枚で `complete` となった。
受付時間が未発表の場合は、現在画像と料金の出典だけで `incomplete` となった。

### 画像専用モード

`--vision --image-only` は、Jev に渡す画面情報を現在の番号付き画像だけに限定する。
`jev/image-only-input.ts` で最終送信内容を許可した項目から組み直し、DOM 本文だけでなく、操作名、タイトル、URL、見出し、過去の本文、別ルート候補のラベルも除く。

## 保存画像による根拠監査

画像入力を使う試行では、各判断直前と探索終了時の画像について、画像 ID、操作番号、URL、ファイル名、縦横サイズ、SHA-256 を保存する。
探索が `STUCK` などで終わっても、保存画像を別の処理で監査する。
画像ごとの読み取り可否と目的との関連性を確認し、関連する画像と最終画像をまとめて達成根拠を判断する。
前の画面にしかない根拠も残す。この処理は探索中の判断を変えず、終了後に行う。

レポートでは、探索の終了理由、画像に基づく判定、既存の DOM 本文による判定を分ける。
画像の欠損・改変や API エラーは「未達」ではなく観測・監査の問題として扱う。
画像を読めない場合や、達成と回答しながら根拠画像を一枚も選ばない場合は「判断不能」にする。
この監査も Jev の判断であり、客観的な成功確認ではない。

Canvas 内だけに情報を描く3条件を、実際の Jev と Playwright で各2回試した。
検証側の期待値は表示内容と保存画像の表示範囲から決め、Jev には渡していない。

- 停止済みの画面：2回とも探索は完了し、画像監査も達成根拠ありと判断した。
- 料金と受付時間が別の画面にある場合：2回とも探索は `STUCK` だったが、画像監査は両方の画面から根拠を選んだ。
- 「このプランでは停止できない」と明記した画面：2回とも、監査は達成と回答しながら根拠画像を選ばなかったため「判断不能」にした。探索側も1回は誤って完了と判断した。

期待する判定との一致は4/6回で、残る2回は判断不能だった。
明確な操作不可の表示を、安定して未達と判断できたわけではない。
失敗結果を成功に書き換えず、モデルの回答の矛盾を残している。
画像監査にかかった時間は1試行あたり約1.5〜4.6秒だった。
記録は `reports/vision-outcomes-2026-10-16T02-27-46.896Z/` の `evaluations.json` と、各試行の画像・判断ログにある。

先の TypeSafe 公開ページの保存画像にも、サイトへ再接続せず監査を実行した。

既存の DOM 監査の「根拠不足」はそのまま残した。
旧ログから取り込んだ画像のハッシュは監査時点で計算した値であり、撮影時の記録ではないことを明示する。

## 達成条件の修正

操作の実現と、操作できないと分かったことを区別するため、画像監査の質問文と選択肢を変更した。
操作を求める目的では操作後の状態を確認し、可否を知る目的では求めた回答を確認する。
操作不可という表示だけで操作目的を達成と扱わない一方、可否を問う目的では「不可」という回答も取得した情報として扱う。
通知停止専用の判定項目や、画面の表示文言を検索する分岐は追加していない。
時系列、後の画面による取消の確認、根拠画像がない場合の保留処理は維持した。

原因の切り分けでは、画像の表示内容を正しく読んだ試行や、同じ内容の転記文でも誤った達成判断が出た。
送信直前の画像ハッシュと参照を照合し、API の生の回答とクライアントの出力も一致した。
直接 HTTP 送信でも同じ誤判定が出たため、この再現ケースを画像伝送や返答変換の問題としては説明できない。
質問文だけ、選択肢だけを明確にする比較では、それぞれ操作不可の画面を 3/3 回、未達と判断した。

## 既存の経路維持との統合

経路維持の処理自体は `ExplorationMemory.commit` と `chooseFrontier` に存在していたが、画像探索では使っていなかった。
前項の `history.recoveryTarget` は候補名を渡すだけで、その処理への引継ぎではなかった。
通常の移動にも未統合部分があったため、Back 後の回復だけでは再訪の繰り返しが残った。

公開サイトの画像探索にも既存の frontier を渡し、通常移動から未探索先の選択と経路の継続を共用するようにした。
完了条件の照合を先に行い、達成を確認した場合は未実行の経路より終了を優先する。
それ以外の移動では、既知の経路を通る間に毎回目先の入口を選び直さず、確定した対象への次の操作を実行する。
元の操作選択と追加の候補判断もログに残す。

Back は現在許可された履歴項目についてのみ、実際に観測した出発状態へ一回分接続する。
過去の Back を固定した将来の経路としては使わない。
戻った観測状態が最新の出発状態と異なる場合は、過去に同じ場所へ戻れたことがあっても経路の継続を解除する。
変わった画面や古い匿名 ID を、そのまま操作しない。

ブラウザの結合テストでは、誤った入口、行き止まり、Back、別の入口、完了の順で動くことを確認した。
戻った後の操作選択には同じ誤った入口をあえて返し、既存の経路維持が別の入口を選ぶことを検証した。
外部の推論サービスだけを置き換えたテストなので、Jev の選択精度を証明するものではない。

実 Jev の再探索では、気象庁の判断 6 で元の操作選択が施設一覧を再選択したが、確定した経路に従ってスクロールした。
経路継続は確認できたものの、6 操作、約 40.8 秒で `STUCK` となり、Goal は未達だった。
この試行は Back 自体を選んでおらず、Back 後の継続の確認は結合テストと区別する。
国立国会図書館は 10 操作、約 63.0 秒で完了し、保存画像で来館時新規登録と本人確認書類を確認した。
記録は `reports/2026-10-16T05-43-00.571Z-public/` と `reports/2026-10-16T05-43-13.192Z-public/` にある。

画像探索では、未探索先の新規選択に追加推論が必要になる。
確定済み経路の継続には対象の選び直しを行わないが、途中でも通常の画像判断と完了照合は維持する。
特定サイトで成功するための入口や正解の回答は追加していない。

## 現在の範囲と制約

探索時の判断入力には現在の画像 1 枚を渡す。
過去画像の文字は、後述の「現在画像と文字メモ」の方式で、Jev が画像との一致を確認した候補だけを保持する。
OCR で候補化できない内容、判読できない文字、図形の意味を保持できるとは限らない。
操作対象は既存の DOM 候補から選ぶため、ラベルを取得できず候補から除外したボタンや Canvas 内の操作は扱えない。
探索済みの状態と操作を識別する既存のメモリも DOM 観測に基づくため、画像だけが変わる同一画面の扱いは今後検証する。

画像監査は各画像を確認してから複数画像をまとめて評価するため、観測画像の数に応じて API 呼び出しと入力が増える。
今回の最小実装では固定枚数で切り捨てていない。長い探索での入力上限と費用は今後の検証対象である。
監査の判定結果を、探索の成功やサイトの UX の良し悪しと直結させない。
DOM の引用を根拠とする `--goal-check` と `--vision` の併用は、現段階ではエラーにする。

API が使用トークン数を返した場合は判断ログに保存する。
費用は API が返した場合だけ記録し、未返却を 0 ドルとして扱わない。
使用量と費用は返答に対応する値であり、失敗したリトライを含む請求総額ではない。

次の検証対象は、未達と判断不能を分ける判定の精度、画像履歴の意味理解と訂正、画像上の操作対象と DOM 候補の対応付けである。

## 現在画像と文字メモ

探索時の画像保持を現在の 1 枚に置き換えた。
過去画像のバイト列を次の判断へ持ち越さず、操作履歴と探索済みの枝は既存コードで管理する。
保存 PNG と終了後の画像監査は、探索判断とは別の証跡として維持した。

Jev は自由文を生成するモデルではないため、観測文を出力できるとは仮定していない。
[公式の質問と回答形式](https://docs.typesafe.ai/introduction)を確認し、既存の Tesseract による OCR を文字候補の生成だけに使った。
疎な文字向けとまとまった行向けの 2 種類の読み取りを行い、候補を画像と Jev で照合する。
確認できた文字だけを、観測 step、URL、画面 ID、表示範囲、画像ハッシュ、文字位置、判定モデルとともに `visualMemory` へ残す。
候補の文字や数値をコードで推測修正しない。
却下と不明の候補は過去の根拠として渡さない。

初版では通常の操作選択と同じリクエストで、空き枠に文字照合の質問を加えた。
現行版では、後述のとおり文字照合を操作選択から分離している。
収まらない候補は追加リクエストで 8 件ずつ照合し、候補数の上限として切り捨てない。
追加分を含む質問 ID、生の回答、通信記録、返却された使用量と費用、途中失敗を `step.visualContext.requests` に保存する。
`decision.request` や `decision.usage` は元の操作判断の返答であり、追加照合を含む全通信の合計ではない。
費用の未返却を 0 として扱わない。

最初に疎文字向け OCR だけを使った方式では、画像内の料金を誤読し、Jev が却下したため、2 回とも画像またぎで未完了となった。
この失敗も `reports/middleware-reliability-2026-10-16T06-28-37.272Z/` に保存した。
2 種類の候補を使った最終方式は、同じ 8 ケースを各 2 回実行し、情報保持 52 照合、保持文字と出典 34 照合で不一致を検出しなかった。
完了 10 回、未完了 6 回、異常終了 0 回で、条件不足や操作不可を完了へ変更していない。
画像をまたぐケースは 2 回とも 1 操作で完了した。
結果は `reports/middleware-reliability-2026-10-16T06-34-47.431Z/` にある。

全画像方式との比較では、探索中に送信した画像は延べ 42 枚分から 34 枚分となり、画像本体の合計は 862,710 bytes から 698,110 bytes へ約 19.1% 減った。
探索中の API リクエスト数は両方式とも 34 回だった。
この集計は frontier と追加の文字照合を含み、終了後の監査は含まない。
バイト数は PNG 本体の値であり、HTTP 全体や請求トークン数ではない。
短い画像またぎケースの探索時間は、旧方式の約 5.1〜5.5 秒に対し、新方式は約 6.0 秒だった。
画像入力の増大は抑えたが、この結果から高速化や費用削減まで確認したとは言えない。

40 観測の配線テストでは、初期の確認済み文字を保持しつつ、各リクエストの画像を 1 枚に保つことを確認した。
このテストは外部推論と OCR を固定したもので、長時間の実サイトでの読み取り精度を証明するものではない。
文字の照合も同じ Jev の判断であり、任意の画像について正しさを独立に保証するものではない。
非文字の視覚情報、OCR が拾えない文字、更新された内容の意味判断は制約として残る。
OCR の初回利用では言語データが必要で、`.cache/ocr` にない場合は取得する。
