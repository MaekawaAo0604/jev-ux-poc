## 実験A：LOOPの原因

既存のガードは、URL、観測された画面全体、選択した操作を JSON 化して一致を数える。
同じ組が3回目になると、操作前に終了する。
判断に使う履歴、ペルソナ、選択確率はこのガードのキーに含めない。

代表的な経路は次の通り。

1. ホームから「各種設定」を選ぶ。
2. 「お知らせ」を選ぶと、実際にはキャンペーンの「今月のおすすめ」へ進む。
3. ホームへ戻る。
4. 再び「各種設定」を選ぶ。
5. 「アカウント情報」を選ぶと「利用履歴」へ進む。
6. ホームへ戻る。
7. 再び「各種設定」を選ぶ。
8. 「アカウント情報」などを選ぶ。
9. ホームへ戻る。
10. 再び「各種設定」を選択し、実行前に LOOP で停止する。

初回の URL は `/bad/`、ホームへ戻った後は `/bad/#home` だった。
観測画面が同じでも URL が異なるため、初回の選択は再訪時の署名とは別に数えられる。
再訪後の4、7、10番目の判断で同じ署名になり、10番目が3回目になる。
全12試行でこの判定を再構成できた。
最後の10番目の選択を、実行した10操作目として扱わない。

分類別の判断は次の通り。

- A、UI・UX：目的への入口「その他」は48回候補に現れ、選択は0回だった。「お知らせ」とキャンペーンの関係など、入口と目的の対応が分かりにくい可能性がある。ただし、人間も同様に迷うかは未検証。
- B、Jev：最終判断には9件の履歴がある。別の入口とスクロールを残したまま、未達だった入口を再選択したことは観測できる。読み落としか、意味の判断か、内部の理由は確定できない。
- C、基盤：ハッシュで遷移する複数画面に、文書単位の同じ `pageId` を割り当てていた不具合を確認した。ID を分離しても3試行とも LOOP が残ったため、これだけでは元の失敗を説明できない。元の108操作には内部の操作エラーがなく、操作後の画面変化も記録されている。各試行1件の外部要求の遮断はあるが、内部遷移の失敗とは区別する。
- D、終了と達成確認：ガードは実装通りに発火している。通知停止の画面・メッセージには到達せず、実際の停止操作も行っていないため、達成確認の false はログと整合する。スクリプト対照と Good UI では同じ達成確認が true になった。
- E、未特定：限定された理由カテゴリから、用語の理解や知識の利用を直接観測することはできない。

旧12試行から分かるのは、繰り返した選択と停止機構、画面 ID の不具合の存在まで。追加実験では画面 ID 修正だけでは改善せず、既存探索処理の接続後に成功した。
UI だけ、または Jev の認識だけを唯一の原因として確定しない。

### 確認できた差の範囲

GitHubの2FA設定ガイドを3操作で読んだ同じ停止状態で、Persona Aを与えると、ペルソナなしよりcompletionCoverageが続行側になる割合が増えた。新規の主要50組ではbaseline 1/50、A 21/50が続行（差40ポイント、片側p=0.0000009536743）。別の確認50組ではbaseline 1/50、A 12/50（差22ポイント、片側p=0.00048828125）。支持方向の不一致ペアは主要20・確認11、逆向きは両群0だった。両群で独立にp<0.01かつ続行率差15ポイント以上という事前基準を満たした。ペア内条件順を事前の固定シードで無作為化し、各群50組で測定を終了した。

画面本文、過去の観測、目的、判定質問、4枚の実画像を固定し、入力差は元の全Persona Aの有無だけ。各応答は新規の独立したAPI呼出で、過去の探索結果をこの検定へ加えていない。符号検定は、終了判定が食い違ったペアの向きを条件付き二項分布で照合する。判定が同じペアも続行率の分母には含めた。

これは、事後に選んだ1つの停止状態で、全ペルソナAの入力が終了判定に影響することを確認した結果。知識だけの効果、初手の選択差、探索全体の再現性、人間の初心者の行動予測は未実証。200件は完了判定コンポーネントの応答であり、200回の実ブラウザー探索やスクロールの記録ではない。既存処理ではcompleteならdone、incomplete/uncertainなら既存の保留中スクロールを継続する。
